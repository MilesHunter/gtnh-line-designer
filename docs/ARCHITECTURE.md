# Architecture

## 进程结构

应用分为三个主要运行区域：

1. Electron 主进程负责便携目录、数据版本、文件选择、项目文件、PNG 导出和本机实例导入。
2. 渲染进程负责 React 界面、节点画布、项目状态和检查器。
3. Web Worker 负责 data v7 二进制解析、机器/物品/配方索引、精确搜索、单节点预览、整图校验和求解。

## 数据流程

### 在线数据

1. 数据管理器从 GitHub 解析固定 Commit。
2. `data.bin` 和 `atlas.webp` 下载到持久化 `.part` 文件。
3. 校验 SHA-256。
4. 原子移动到 `data/cache/<commit>/`。
5. 更新 `data/selected.json`。

### 本机 NESQL 导入

1. 用户绑定包含 `mods` 的 GTNH `gameDir`。
2. 应用根据版本和模组文件选择 NESQL 配置。
3. 准备导出环境时，BugTorch 和冲突 JAR 被移动到可恢复 session 目录。
4. 用户手动启动游戏并执行 `/nesql <repo>`。
5. 应用检查日志、数据库和图片文件稳定性。
6. 内置转换器将 HSQLDB 导出转换为 data v7 和 WebP 图集。
7. 成功数据写入独立的 `local-<fingerprint>` 缓存。

## 图和求解

当前项目格式为 `ProjectDocument` schema v2，保存具体机器、可选配方 ID、边、位置、视图和求解设置，不嵌入完整配方或图标数据。旧版 `ProjectDocumentV1` 在打开时通过当前配方数据解析具体机器并迁移。

左侧有两个独立入口：

- 机器搜索只枚举配方索引中出现的具体单方块/多方块机器，可创建未配置配方的空节点。
- 原料/产物搜索使用具体物品、流体或矿辞芯片；普通物品同时匹配包含它的矿辞，两边都填写时取配方交集。

多机器配方在结果中展开为具体机器卡片，玩家必须明确选择机器后才能创建节点。

节点预览与整线求解分离。修改机器、配方、电压、线圈、并行或机器数后，Worker 只计算该节点的理论端口吞吐和功率；这些值不参与连线流量分配。等效机器数允许小数，向上取整仅作为建造建议。

电压低于配方基础等级时节点无效。只有实际电压高于配方基础等级时才按机器规则进行普通或完美超频；多方块并行按机器公式单独计算。只有规则中存在线圈参数的多方块机器显示线圈配置。

求解完全由用户触发。每次点击“计算”时，Worker 根据节点配置构建物料和功率方程，通过 `javascript-lp-solver` 计算：

- 节点实际速率
- 边流量
- 外部原料
- 外部盈余
- 概率产出
- 回收环
- 各节点和电压等级功率

计算前会校验空节点、缺配方、机器不兼容、电压不足、目标无效和连线兼容性；任何错误都会阻止求解并高亮。端点已不存在的悬空连线静默清除。

拓扑、节点配置或连线变化后，旧结果保留并标记为“已过期”，等待下一次手动计算。计算使用模态阶段进度，可取消；取消会重建 Worker 并保留当前项目和过期结果。

编辑器以 500 节点、1,000 条边为验收规模。画布只渲染可见节点，节点数据按对象身份复用；拖动只替换被移动的节点对象。撤销历史只保存发生变化的节点和边，不复制整张图。

## 便携目录

```text
data/
  cache/<commit>/
  selected.json
  settings.json
  local-source.json
workspace/
logs/
```

应用启动时检查自身目录是否可写。运行时不回退到 `%APPDATA%` 保存配方数据。
